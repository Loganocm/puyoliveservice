Findings: `NET-01` to `NET-12` in the [register](/review/findings/). The
target design is [authoritative rollback netcode](/architecture/netcode/).

## The situation in one paragraph

The client tells the server how much garbage it sent and whether it lost, and
the server believes it (NET-01, NET-02). The server does run the same engine
for each player, but that simulation was switched off as an authority because
it disagreed with the clients and produced false losses. The README attributed
that to network latency. The actual cause is more specific and fixable: the
server steps its simulation from a drifting 16 ms interval and applies inputs
when they *arrive* rather than at the frame they are *stamped* with (NET-04),
and garbage enters each player's tray at whatever frame the packet happens to
land (NET-05). The server was simulating a different game from the one being
played.

## Why this is closer to fixed than it looks

The hard parts are done:

- **Every input is frame-stamped** and every frame means the same instant on
  both machines ([shared clock](/decisions/0003-shared-match-clock/)).
- **The opponent's board is already reconstructed from their input stream**
  with a jitter buffer ([ADR 0004](/decisions/0004-opponent-simulation/)).
  That is exactly the mechanism a server needs to simulate a player
  faithfully.
- **The engine is deterministic and shared.**

What is missing is small by comparison:

1. **Step the server's simulations by the shared clock**, a fixed delay behind
   live (the same jitter buffer idea), applying each input at its stamped
   frame. Then the server's result is not an approximation; it is the match.
2. **Make garbage delivery a function of the match**, not of the network:
   garbage generated by player A at frame *f* enters player B's tray at frame
   *f + D* for a fixed delivery delay *D*. Every machine, including the
   server, computes the same answer.
3. **Let the server decide garbage and top-out**, and have clients predict
   locally and correct on disagreement (rollback) instead of trusting
   themselves.

## Other integrity gaps

- **Loss dodging** (NET-03). A disconnect records a loss; going silent for
  seven seconds aborts with no result. Policy recommendation: a 20-second
  reconnect window during which the player's board keeps running (garbage still
  lands), then forfeit. Aborts without penalty only when *both* players drop or
  the server fails.
- **Stalling** (RUL-05) lets a losing player freeze the match. Fixed by a
  lock-reset budget in engine v2.
- **Seeds** (NET-08) should come from a CSPRNG. Clients will still be able to
  compute the whole sequence, since client-side prediction requires it; that is
  an accepted trade-off in the genre.
- **Reconciliation hides bugs** (NET-11). The opponent view silently overwrites
  its simulated board with 2 Hz snapshots when they disagree. NET-06, an
  unrecorded input path, went unnoticed because of it. Divergence should be
  counted and reported as telemetry, with the board restored only as a last
  resort.
- **Version skew** (NET-12). The client and the server deploy separately, so a
  long-lived tab can run old rules against a new opponent. A handshake that
  compares `ENGINE_VERSION` and refuses mismatches is cheap insurance.

## Scale

All state lives in one Node process (NET-10). That is fine at today's size, and
premature distribution would be a mistake. But a deploy currently kills every
live match, which is a player-visible failure every time a change ships. The
first fix is operational, not architectural: **drain before swap** (stop
matchmaking, let running matches finish, then restart). Horizontal scale
(a gateway plus room servers with Redis for presence and queues) is phase 4.

## Matchmaking

Pairing is first-in, first-out (NET-09). Good matchmaking pairs players of
similar rating, widening the acceptable gap as wait time grows, and it needs a
rating system that knows how *certain* each rating is. See
[rating and matchmaking](/architecture/rating-and-matchmaking/).
